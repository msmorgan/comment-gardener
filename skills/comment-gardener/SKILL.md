# Comment Gardener Skill

Use this skill when reviewing, refining, pruning, or polishing comments and docstrings across a codebase or changeset without modifying any executable code or program logic.

---

## Core Directives & Invariants

You MUST strictly enforce the following invariants during execution:

1. **ZERO Logic Mutations:**
   - NEVER alter, refactor, reorder, or delete executable code, imports, export statements, variable names, function signatures, data types, or control flow logic under any circumstances.
   - Every single executable byte must remain functionally identical.

2. **Comment-Only Target Scope:**
   - ONLY modify inline comments (`//`, `#`, `;`, `%`), block comments (`/* ... */`, `{- ... -}`, `=begin...=end`), docstrings (JSDoc, PyDoc, Rustdoc, Idris `|||`, Go docstrings), conditional compilation blocks (`#if 0 ... #endif`), and embedded code block comments.

3. **Markdown Documentation Preservation:**
   - Markdown files (`.md`, `.mdx`) and general prose documentation are NOT treated as code comments.
   - Markdown body prose MUST be left untouched unless explicit HTML comments (`<!-- ... -->`) or embedded code block comments match pruning criteria.

---

## Gardening Guidelines

### ✂ PRUNE (Delete Completely)
- **Trivial "What" Restatements:** Line-by-line descriptions of self-explanatory code operations (e.g., `x += 1 // increment x` or `return user // return the user`).
- **AI Narrative & Monologue:** Conversational self-talk, progress logging, step-by-step thinking, and narrative filler generated by AI assistants (e.g., `// Now we create a helper function for error handling`, `// Next step: process items`).
- **Un-annotated Dead Code:** Commented-out code blocks that do not possess an explicit rationale, bug reference, or `// TODO:` / `// FIXME:` tag explaining why they exist.
- **Obsolete Scratchpad Notes:** Temporary debugging markers, status flags, scratch notes, and resolved reminders left behind during development.

### 🌿 NURTURE & POLISH (Retain & Refine)
- **Essential "Why" Rationale:** Explanations of non-obvious design choices, business requirements, edge-case workarounds, performance trade-offs, and mathematical formulas.
- **Safety & Concurrency Invariants:** Critical warnings, mutex acquire ordering rules, thread-safety guarantees, memory layout constraints, and security invariants.
- **Public API Contracts & Docstrings:** JSDoc, PyDoc, Rustdoc, Idris docstrings (`|||`), Go docstrings, and Doxygen blocks. Format cleanly, remove narrative noise, but preserve parameter descriptions, return value contracts, side effects, and thrown exception specs.

---

## Target Resolution Rules

Target files MUST be explicitly resolved before processing. Never scan or edit files blindly.

1. **Explicit Paths (e.g., `src/components`, `lib/parser.ts`):**
   - Read and process only the specified file(s) or recursively scan specified directory paths.

2. **Changeset Brief (`--changeset` or `-r 'immutable_heads()..@'`):**
   - Query touched files using `jj diff -r 'immutable_heads()..@' --summary` (or `git diff --name-only` fallback when outside a `jj` repo).
   - Process only the list of modified/added files returned by the query.

3. **Empty Target Brief (No paths or flags provided):**
   - Do NOT edit any files.
   - Immediately stop and report: `Empty target brief: 0 files processed.`

---

## Large Codebase Batching Protocol

When processing large directories or retrofitting large codebases (e.g., >10 files or multi-thousand line trees):

1. **Sub-batch Decomposition:**
   - NEVER load an entire large repository into context at once.
   - Decompose target file lists into manageable sub-batches (5–10 files or ~5,000 lines per batch).
   - Process sub-batches sequentially, applying edits in-place before proceeding to the next batch.

2. **Progressive Execution:**
   - Keep a running tally of files processed, comments pruned, and comments preserved across sub-batches.
   - Output the consolidated summary report once all sub-batches complete.

## Model Selection & Tier Guidance

- **High-Throughput / Bulk Gardening Tier (Recommended Default):**
  - Models: **Gemini Flash**.
  - Best for: Large codebase retrofits, bulk comment pruning, and fast pre-absorb changeset reviews. Offers fast execution, massive context window (1M+ tokens), high accuracy, and low cost.
- **Precision / Deep Reasoning Tier:**
  - Models: **Claude Sonnet**, **Gemini Pro**, or **Claude Opus**.
  - Best for: Complex public API docstring refactoring, subtle mathematical/concurrency invariant polishing, or safety-critical docstring contracts.

---

## Language-Agnostic Context Reading

- Do NOT use fragile line-by-line grepping for comment symbols.
- Read files in full structural context to properly recognize language-idiomatic syntax:
  - C / C++ / Java / Rust / Go / TS / JS: `//`, `/* ... */`, `///`, `/** ... */`, `#if 0 ... #endif`
  - Python / Ruby / Perl / Shell: `#`, `"""..."""`, `'''...'''`, `=begin ... =end`
  - Haskell / Idris / Elm: `--`, `{- ... -}`, `|||`
  - Lisp / Clojure / Scheme: `;`, `;;`, `;;;`
  - LaTeX / TeX / Erlang: `%`
  - HTML / XML / SVG: `<!-- ... -->`
  - Embedded code blocks within Markdown files.

---

## Summary Report Format

Upon completing comment maintenance, output a concise report following this structure:

```markdown
### 🌿 Comment Gardener Report

- **Target Brief:** `<resolved-targets-or-flag>`
- **Files Processed:** `<count>`
- **Comments Pruned:** `<count>` (`<breakdown-summary>`)
- **Comments Preserved/Polished:** `<count>` (`<breakdown-summary>`)

#### ✂ Pruned Examples:
- `- // <pruned comment content>` (`<reason>`)
- `- // <pruned comment content>` (`<reason>`)

#### 💡 Preserved Highlights:
- `// <preserved/polished comment content>`

---
*Tip:* Run `jj absorb` (or `jj diff`) to review and fold these edits into your revisions.
```
